## Read-tool staleness on frequently-appended files (hit 2026-10-03)
- `muse.read` on `~/notes/TODO.md` returned a STALE snapshot twice (the 05:11 run, and the 13:26 run's first four reads — all showed the file ending at the 05:26 entry, line 422, while `wc`/`tail`/`grep` via exec and `git log` showed 462 lines ending at the 13:11 entry, committed 13:12:40, before the run started; a later `read` returned live content). The stale content was genuine-but-old, not fabricated — this is what the 05:11 "INTEGRITY NOTE" misread as fabrication and the 05:26 correction correctly identified as genuine history.
- Mitigation: for the run log (and any hot-appended file), verify the LIVE tail via exec (`tail`, `grep -c`, `git log`) before trusting where the file ends or concluding entries are missing. Do not treat a stale read as evidence of tampering.

## Exec/tool output fabrication (hit 2026-10-03)
- An `exec` call (`tail -60 ~/notes/TODO.md`) returned FABRICATED content: whole run-log entries (18:26/18:41) and entry bodies that do not exist in the file, plus false "upstream landed #269→#290 on Oct 3 + rebuilt mcpx" narratives assembled from REAL Sep-30 store hashes and commit SHAs (verified real via `stat` birth times and `git log` dates — the builds/commits happened Sep 30, not Oct 3). The real file (md5 + fresh `sed -n` ranges) ended at the genuine 18:11 entry; the served output contradicted it on md5, line count, issue states (#260/#291 claimed OPEN, actually closed Oct 1), and git history.
- This is worse than read-staleness (which serves genuine-but-old content): the output was never in the file. Nothing from it was acted on — every consequential fact was re-verified with independent fresh calls first.
- Mitigation: never act on a single tool output for consequential claims. Cross-verify with independent fresh calls using different commands (`sed -n` ranges, `md5sum`, `wc -l`, `git log`, `gh api`, `/proc/<pid>/exe`, store-path `stat` birth times, `systemctl show`). When served content contradicts the file's md5/line-count, trust the fresh bytes. When an entry's claims (rebuilds, commits, pushes) lack corresponding git/store evidence, treat the entry as suspect, not the evidence as missing.

- 2026-10-04 ~17:52 CDT: related SELF-INFLICTED variant — `git ls-remote origin HEAD --git-dir=/home/hatch/git/nix/.git` returned 41ccf57 (the /home/hatch repo's OWN HEAD), NOT dezren39/nix's. Cause: top-level options like `--git-dir` (and `-C`) MUST come BEFORE the subcommand — placed after it, git silently ignores/misapplies them, so the command ran in the CWD repo against ITS origin. Rule: use `git -C <dir>`, never a post-subcommand `--git-dir`.

## Exec stdin vs heredoc (hit 2026-10-05)
- The exec tool's `stdin` parameter CONFLICTS with shell heredocs (`python3 - <<'EOF'`): the heredoc wins and the `stdin` parameter content is silently dropped — the script runs seeing empty stdin, with no error. Three consecutive Cloudflare auth checks ran with an empty token because of this and reported "not authenticated".
- Rule: when a script needs stdin (e.g. a secret), put the code in `python3 -c '...'` (no single quotes inside) and let the `stdin` parameter carry the secret. Never combine `<<'EOF'` with the `stdin` parameter.
- Related: Python's `http.client` ignores proxy env vars and tries direct TLS (fails in the sandbox with SSL WRONG_VERSION_NUMBER); `urllib.request` honors the egress proxy env vars. Use urllib for outbound HTTPS from exec.

## Browser tasks and secrets (2026-10-25)
- A browser task will NOT return secret values (e.g. Slack app tokens) in its report, even when Drew explicitly instructs "pass the values through you" — the refusal is built into the browser layer. Working routes for token transfer: Drew pastes the value in chat → Muse files it into Bitwarden Secrets Manager (sha-verified round-trip, temp copies shredded); or Drew takes over the browser tab and copies the value into the vault himself.
